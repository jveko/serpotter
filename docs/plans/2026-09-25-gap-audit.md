# Gap audit 2026-09-25 — full agent reports

## Report: DataLayerGaps

## Findings

**1. P2 — Query-cache key is FNV-1a 64-bit (forgeable) and is NOT service-scoped, contradicting the DDL contract**
Evidence: `crates/serpotter-product/src/cache.rs:26-36` (`fnv1a64` + `key_hash()` = 16 hex of a non-crypto hash of caller-controlled text); migration `crates/serpotter-db/migrations/0015_feature_wave.sql:4-7` claims `key_hash` is "the service-aware content hash minted by the product layer" and makes it the sole PRIMARY KEY; but the canonical strings (`cache.rs:74-103`, `112-171`) contain no service prefix. Why it matters: FNV-1a is trivially invertible, so any token holder can append collision-extension bytes to their own query to hit another user's cache row and read/overwrite their cached response (cross-query poisoning); and a cross-surface collision silently rewrites `service` via `cache.rs:52-63` `ON CONFLICT(key_hash) DO UPDATE SET service = excluded.service`, evicting the other surface's row. Fix: hash with the already-present `sha2` dependency (`keys/admin_crud.rs:8-13` has `sha256_hex`) and prepend the service into the hashed input.

**2. P2 — `/api/usage` days contract drift: API clamps 1..180, DB silently clamps 1..90**
Evidence: `crates/serpotter-api/src/admin/usage.rs:65` `q.days.unwrap_or(14).clamp(1, 180)` vs `crates/serpotter-db/src/usage.rs:85` `days.clamp(1, 90)`. Why it matters: `?days=120` returns only 90 days of data with no error or echo, so the SPA can render a chart labeled 120d that is silently truncated. Fix: align both clamps to one documented bound (single constant exported by serpotter-db).

**3. P2 — The concurrency contract of `acquire_api_key_shared` (optimistic `inflight < ?` guard) is structurally untestable with the in-memory pool; prod's WAL/5-connection config is never exercised**
Evidence: `crates/serpotter-db/src/keys/acquire_report.rs:81-96` (UPDATE … `WHERE id = ? AND active = 1 AND inflight < ?`, rows_affected==0 → `None`); `crates/serpotter-db/src/lib.rs:79-83` forces `max_connections=1` for `:memory:` — so `pool.begin()` serializes all txs in every test (keypool/`tests.rs`, db `migrate.rs`), and no test in the workspace runs a file-backed WAL multi-connection pool (grep of `connect_and_migrate` call sites: all `sqlite::memory:` except `main.rs:38`). Why it matters: the exact lost-race path and any SQLITE_BUSY behavior under WAL with 5 writers has zero coverage; an sqlx/pool upgrade could regress it silently. Fix: add one on-disk (tempdir) multi-connection test spawning concurrent acquires.

**4. P3 — Dead column `api_keys.email`**
Evidence: `crates/serpotter-db/migrations/0003_api_keys.sql:7`; no SQL, row struct, or handler anywhere references `email` (workspace grep: only the DDL). The crate already sets precedent for deleting dead schema (0016 dropped dead B22 columns, 0017 dropped request_log). Fix: drop it in migration 0019.

**5. P3 — Dead method `Db::bump_node_inflight`**
Evidence: `crates/serpotter-db/src/nodes.rs:272-279`; zero callers in the workspace including tests and `serpotter-db/AGENTS.md`'s API table (workspace-wide grep matches only the definition). Fix: delete it.

**6. P3 — `admin_sessions.user_id` FK is declared but never enforced (no `PRAGMA foreign_keys=ON`)**
Evidence: `crates/serpotter-db/migrations/0008_admin_sessions.sql:9` (`REFERENCES admin_users(id)`); `connect_and_migrate` sets only `journal_mode` (`lib.rs:71-91`) — SQLite defaults FKs OFF and the repo never enables them. Why it matters: any future user-delete path would orphan live sessions that `get_valid_admin_session` (`admin_auth.rs:133-150`) keeps honoring by `user_id`. Fix: enable `foreign_keys(true)` on connect or drop the fake constraint from docs.

**7. P3 — Per-acquire reclaim UPDATE and the re-enable cron scan `api_keys`/`nodes` with no supporting index**
Evidence: `acquire_report.rs:7-8` `UPDATE api_keys … WHERE lease_until IS NOT NULL AND lease_until <= datetime('now')` runs inside **every acquire transaction** (`acquire_report.rs:52`), and `admin_crud.rs:293-301` (`active = 0 AND disabled_reason IS NOT … AND last_used_at < …`) every 15-min tick; existing indexes are only `(service)` and `(service, active)` (`0003:17-18`) — no index covers `lease_until` or `(active, last_used_at)`. Harmless at ~3k rows, but it's a full table write-scan on the hottest request path. Fix: partial indexes `WHERE lease_until IS NOT NULL` (keys + nodes).

**8. P3 — `KEY_REENABLE_AFTER_HOURS=0` disables fail@3 backoff instead of tuning it; no floor validation**
Evidence: `crates/serpotter-api/src/cron.rs:66` reads the env; `crates/serpotter-db/src/keys/admin_crud.rs:291` `hours.max(0)` → predicate `last_used_at < datetime('now','-0 hours')` is true for every idle inactive row, so every non-`vendor_suspended` disabled key returns to rotation on the next 15-min tick. `env_i64_or` only warns on unparseable values, not on 0. Fix: clamp to a sane minimum (or treat 0 as "cron disabled") and warn.

**9. P3 — Migration 0018's header comment misdescribes the fail@3 contract that the code implements**
Evidence: `0018_key_disabled_reason.sql:8-9` says `'manual'` = "operator toggle **or a fail@3 auth hard-disable**", but `report_api_key_failure` (`acquire_report.rs:154-168`) intentionally leaves `disabled_reason` NULL on hard-disable (per the same file's backfill rationale, lines 18-24, and `keys/rows.rs:30-32` which says manual = operator toggle only). Why it matters: an operator reading the migration header will expect fail@3 rows to be queryable as `'manual'` and will mis-triage. Fix: one-line comment correction in the migration file text is impossible post-merge (checksum) → note it in `AGENTS.md` instead.

**10. P3 — In-crate docs drifted to a stale schema version and dropped table**
Evidence: `crates/serpotter-db/AGENTS.md:7` "`EXPECTED_SCHEMA_VERSION` must match last migration bump (currently **17**)" vs `src/lib.rs:26` = 18; `crates/serpotter-api/src/admin/logs.rs:1` still titled "Admin request_log browser" though the table was dropped in 0017 and the handler reads the in-memory ring (`logs.rs:66-92`); `serpotter-product/src/cache.rs:20` comment "(matches request_log `service`)" references the dropped table. Fix: update the three doc lines.

**11. P3 — Admin `/api/keys/sync` serializes one upstream fetch + one UPDATE per key inside the request**
Evidence: `crates/serpotter-api/src/credit_sync.rs:40-116` loops all active keys sequentially, `fetch_usage` per key then `update_api_key_usage` per key; with the pool at ~3,098 keys (`admin_crud.rs:232-269` prod-log analysis) a single admin sync request is O(keys) upstream round-trips and O(keys) individual DB writes with no pagination/limit. Cron side is default-off (`cron.rs:100-116`), but the manual endpoint has no cap. Fix: bound the batch or move it to a spawned job returning a report id.

**12. P3 — WAL write-contention knobs (busy_timeout, synchronous) are never configured; behavior depends on sqlx defaults**
Evidence: `crates/serpotter-db/src/lib.rs:71-95` sets only `journal_mode(Wal)` and `create_if_missing`; no `.busy_timeout()`/`.select()` pragmas anywhere. [INFERENCE] sqlx 0.9 (`Cargo.lock:1886-1887`) ships a 5s default busy timeout, but the repo never pins it, so an sqlx upgrade that changes the default turns WAL write conflicts into user-visible `DbError::Sqlx` 500s on hot single-statement paths (`release_*_inflight`, `upsert_usage_daily`). Fix: set `.busy_timeout(Duration::from_secs(5))` explicitly.

**Why it matters:** the table is the documented authority for routing (`crates/serpotter-core/AGENTS.md:24-25`) and 3/16 rows plus a whole gate can never fire, so edits there cannot be validated by behavior; advertised dials (`mode=web`) do nothing.
**Fix:** delete the dead rule arms + Gate 6 + `other` arm (or add `match_mode:"web"`/`intent:"auto"` handling) and pin each remaining rule with a test that reaches it through `route_search` with boundary-legal input.

### P2 — Deep research ignores/contradicts the knobs the standard loop honors
**Evidence:** `extract/research.rs:470-473` `scrape_n = body.scrape_top_n.unwrap_or(3).clamp(1, DEEP_MAX_SCRAPE as u32)` — an explicit `scrapeTopN: 0` (documented "0–10" at `api/mcp/params.rs:301`, honored as "no scraping" by the standard path at `research.rs:122-123`) becomes 1 and costs a vendor scrape. `research.rs:694-695, 723-726` hard-set `social_results: None, social_error: None` and never read `social_max_results`/`allowed_x_handles`/`excluded_x_handles`, so a deep request that names X handles gets neither results nor a warning (the standard loop runs the social leg at `research.rs:214-370`).
**Why it matters:** one DTO, two loops, silently different accepted-knob sets — the caller cannot tell a skipped leg from a failed one.
**Fix:** honor `scrape_top_n == 0` (skip scraping) and surface an ignored-knob note in `evidence.web_leg_errors` when `deep` drops social/handle input.

### P2 — Deep-research refinement dedupes on raw URLs, contradicting the `normalize_url` contract
**Evidence:** `extract/research.rs:619-622` `if !web_items.iter().any(|w| w.url == item.url)` and `:630-636` `!known.contains(&i.url.as_str())` — plain string equality. The same "is this the same page" question is answered with `normalize_url` in `pipeline.rs:39` and `execute.rs:33-46`.
**Why it matters:** pass-2 results differing only by `www.`, trailing slash or `utm_*` count as "novel", so the loop re-scrapes an already-scraped page (directly contradicting the comment at `research.rs:649-650`, "never re-scrape an already-scraped page"), duplicates citations (`research.rs:700-708`) and burns the refine budget.
**Fix:** compare `normalize_url(...)` on both sides, reusing the pipeline's key helper.

### P2 — Extract and research-social retries have no backoff (the C2b fix landed on search only)
**Evidence:** `search/run_provider.rs:283-291` sleeps `retry_backoff_ms(attempt)` (150–1000 ms, `:132-141`) before each retry-class continue; `extract/extract_url.rs:326-334` emits `Retry` and `continue`s with **no sleep**, and `extract/research.rs:335-347` (xAI social leg, 3 attempts) likewise. Both loops are otherwise the same ladder with the same retry classes (`Http`, 429, 5xx, 401/403, banned).
**Why it matters:** a 5xx/transport storm gets three immediate re-fires per provider on the extract surface (and per pass on research), then falls through the whole chain — the burst behaviour C2b was introduced to prevent.
**Fix:** call the shared `retry_backoff_ms` before `continue` in `try_extract_provider` and the social leg (move it next to `lease.rs`).

### P2 — `ReportMode` mapping is triplicated, and two copies carry a doc claiming a difference that doesn't exist
**Evidence:** `search/run_provider.rs:30-47` and `extract/extract_url.rs:164-182` are byte-equivalent to `lease.rs:96-118 verdict_for` (both even map `ProviderError::Http(_) => Retryable` at `run_provider.rs:47` / `extract_url.rs:181` vs `lease.rs:115`), yet `run_provider.rs:21-23` and `extract_url.rs:154-156` both state: "Same classes as the shared `verdict_for`, **EXCEPT** transport (`Http`) errors are retryable here". Duplicate pinned tests: `run_provider.rs:374` and `extract_url.rs:1358` assert the identical case. `lease.rs:307-320` inlines the tunnel-vs-key blame decision instead of reusing `report.rs`.
**Why it matters:** three authorities for one key-health rule; the drift the docs promise to keep separate does not exist, so a future edit to one copy silently diverges from the other two.
**Fix:** delete both `report_mode` copies, call `verdict_for`, and drop the stale EXCEPT sentence.

### P2 — `vendor_suspended` is described as self-healing in product docs but schema 18 made it permanent, on a loose substring match
**Evidence:** `search/banned.rs:9-11` ("instantly out of rotation but **self-healing via `KEY_REENABLE_AFTER_HOURS`** if the matcher over-fired") and `hold.rs:151-152` ("self-heals via the `KEY_REENABLE_AFTER_HOURS` cron if it was a false positive") both contradict `lease.rs:292-299` ("the 24h re-enable cron **now skips**"), `migrations/0018_key_disabled_reason.sql:11-15`, `db/src/keys/admin_crud.rs:297` (`disabled_reason IS NOT 'vendor_suspended'`) and the passing test `db/tests/migrate.rs:436-453`. The trigger is `LIKELY_BAN_MARKERS = ["banned","suspended","deactivated","revoked"]` (`banned.rs:26`) matched anywhere in a 401/403 body (`banned.rs:44-51, 65-71`).
**Why it matters:** an over-fire (a proxy/middleware 403 page using the word "suspended") permanently removes a funded key with no automatic recovery, while the two comments the next maintainer reads promise the opposite.
**Fix:** correct both comments to "operator re-enable only", and gate the likely tier on a phrase (e.g. `account … suspended`) rather than a bare word.

### P3 — `"auto"` extract provider is answered four different ways by the four public entry points
**Evidence:** `extract/extract_url.rs:68-77` — `Some("auto")` falls to `Some(other)` → `ExtractError::Provider("unknown extract provider auto")` → **502**; `extract_url.rs:376` explicitly accepts `None | Some("auto") | Some("firecrawl")` → 200 path; `extract_url.rs:845-853` (question) and `:949-957` (highlights) accept only `None` → **400** on `"auto"`; `extract_batch_dispatch` (`:709-725`) routes `"auto"` to Tavily. `cache.rs:118-119/139` normalize `auto == None`, and `api/mcp/params.rs:100-102` accepts `auto` at the boundary; only `extract_dispatch:596-600` filters it, so the three other `pub` entries (`lib.rs:14-20`) misbehave for a documented member.
**Why it matters:** the same value is unset, 400, or 502 depending on which exported function a caller reaches; comments at `extract_url.rs:16,583,1505,1511` also reference a `chain_for` that does not exist.
**Fix:** normalize `"auto"`/blank to `None` inside `fold_extract_provider` so every entry point sees one value, and rename the stale `chain_for` comments.

### P3 — Dead public API whose own docs/tests still claim it is the authority
**Evidence:** `report.rs:22-31 classify_proxied_http` is `pub` (`lib.rs:23`) but has zero production callers (`lease.rs:313-320` inlines the logic); `crates/serpotter-product/AGENTS.md:39` still names it "Dual-pool blame matrix". `extract/helpers.rs:8-31 merge_providers_consulted_real` is `pub` (`lib.rs:18`) with zero production callers (replaced by `meta.providers_consulted`, `research.rs:380-389`), and two of its four tests (`helpers.rs:120-123` and `:142-145`) are byte-identical to each other while asserting the opposite of their own doc comment (`helpers.rs:6-7` "dial labels … never leak" vs `merge_providers_consulted_real(vec!["blend"], …) == ["blend", "firecrawl"]`).
**Why it matters:** dead code with a documentation claim is worse than no code — the next audit reads it as the live rule.
**Fix:** delete both functions, their tests and the AGENTS row; keep the inline ladder logic as the single source.

### P3 — Cache keys interpolate unquoted client text, so distinct requests can collide
**Evidence:** `cache.rs:144-146` `"urls={}|preferred=…", urls.join(",")` — `urls = ["https://a/?x=1,2"]` and `urls = ["https://a/?x=1","https://a/?x=2"]`-shaped lists with a comma-bearing URL produce byte-identical canonical strings (batch `urls` are never canonicalized, unlike search domains). Same shape in `cache.rs:81-83`/`:163` (`query={}` unquoted, so a query containing `|provider=Some("tavily")|…` can alias another row) and `:85` (`sources` join). Keys are then FNV-1a-64 only (`cache.rs:25-37`), with no raw-key column to detect a mismatch on read.
**Why it matters:** `cache_get` (`cache.rs:186-192`) serves the stored JSON verbatim, so a colliding key returns another caller's extraction with 200 + `cache_hit:true`.
**Fix:** serialize each list/field with `{:?}`/length-prefix (or store the canonical string alongside the hash and compare it on read).

### P3 — Error-class drift in three request-shape paths
**Evidence:** (a) `search/mod.rs:127-131` returns `SearchExecError::Search("missing_query")` → 502 `SearchError`, `retryable:true` (`api/src/product/errors.rs:32`), although `error.rs:16-27` defines `InvalidRequest` as the request-shape variant and both boundaries already 400 it (`api/product/search.rs:71-99`) — so it is both mis-classed and unreachable from prod. (b) `extract/research.rs:994-1000, 1021-1027, 1063-1072` synthesize `ProviderError::Upstream { status: 0 }`, which `map_tavily_poll_error` (`:949-951`) renders to the client as "tavily research upstream error (status 0)" — a real transport/start failure reported as a bogus vendor status. (c) `extract/extract_url.rs:813-815 resp_json` uses `unwrap_or_default()`, so a serialization failure writes an **empty-string** cache row instead of skipping the put (the other five call sites guard with `if let Ok(json)`).
**Why it matters:** mis-classed/aliased errors change `retryable`, request_log status_type and operator diagnosis for the same underlying fault.
**Fix:** use `InvalidRequest` for `missing_query`, a real status (0 → 502 `Http` class) for synthetic poll errors, and drop `resp_json`'s silent-default in favour of the guarded `to_string`.

## Report: McpGaps

# serpotter MCP audit — gaps found

Scope read: `crates/serpotter-api/src/mcp/{mod,auth,params,progress,errors}.rs`, `serpotter-auth/src/lib.rs`, `serpotter-api/src/{lib,events,product/*}.rs`, `serpotter-product/src/{lease.rs,meta.rs,extract/*,search/*}`, `tests/{mcp_stateless,mcp_session,mcp_tools,body_limit}.rs`, `docs/ops/{api,env,deploy}.md`. Spec claims verified against the published 2026-07-28 MCP tools spec (fetched).

## Findings

### P1-1 — Error results put a non-conforming object in `structuredContent` while `outputSchema` is advertised
**Evidence:** `crates/serpotter-api/src/mcp/errors.rs:35` (`CallToolResult::structured_error(value)` → envelope into `structuredContent`) with `errors.rs:28-34` (body = `{kind,message,requestId,retryable}`); the advertised schema is the response type at `mcp/mod.rs:203,232,262` (`output_schema::<SearchResponse/ExtractResponse/ResearchResponse>`). The suite *pins* the violation: `tests/mcp_stateless.rs:486` (`structuredContent["kind"] == "ValidationError"`), `:574`, `:609`, `:658`, and `mcp/progress.rs:146-152`.
**Why it matters:** the 2026-07-28 spec is explicit — "Servers **MUST** provide structured results that conform to this schema" (Tools → Output Schema), and the spec's own Tool Execution Error example carries `content` only, no `structuredContent`. Conforming clients (the MCP TypeScript SDK validates `structuredContent` against `outputSchema` and advertises the schema so clients validate too) will reject every failed tool call as a protocol violation instead of surfacing the actionable message — destroying exactly the self-correction path the envelope was built for. `docs/ops/api.md:155` documents `structuredContent` only as "the typed camelCase response object".
**Fix:** set the envelope in `content` only (drop `structured_content` when `is_error`), or make `outputSchema` a discriminated union of success|error.

### P1-2 — MCP `extract_url` batch mode is unreachable: `url` is required even though it is documented as ignored
**Evidence:** `mcp/params.rs:244` (`pub(crate) url: String`, no `Option`/`default`) → schemars emits `url` in `required`; `params.rs:243` description "single-URL modes; **ignored when urls is set**" and `:260` "B26 batch extract … single `url` ignored when set". REST deliberately allows the omission: `product/extract.rs:28-30` (`has_batch` … `if body.url.trim().is_empty() && !has_batch`). No test in `mcp/params.rs:440-727` or `tests/mcp_tools.rs` ever builds an extract request without `url`.
**Why it matters:** the identical body succeeds on `POST /api/extract` and 400s on MCP with `invalid args: missing field \`url\``. Strict clients that generate arguments from the advertised `inputSchema` can never discover or call B26 batch extract, and the failure text is an rmcp serde error, not the documented envelope vocabulary.
**Fix:** make `url: Option<String>` in `ExtractParams` and reuse REST's `has_batch` gate in `validate_extract_params`.

### P2-3 — `tokio::select!` races the deadline against a *completed* product future; REST does not
**Evidence:** `mcp/mod.rs:461-504` — plain `tokio::select!` (no `biased;`) with branches `call(product, req)`, `cancel`, `tokio::time::sleep(request_timeout)`. REST uses `tokio::time::timeout` (`product/mod.rs:95-98`), which polls the inner future first and only then the timer.
**Why it matters:** `select!` polls branches in **random** order, so when a research/extract finishes in the same tick the deadline elapses, MCP can discard the real `Ok` outcome, answer a `Timeout` envelope, log a 504/Timeout row and record no usage/cost — after the vendor call already succeeded and was paid for. Same request, two surfaces, opposite outcomes.
**Fix:** add `biased;` to the `select!` (or wrap the call in `tokio::time::timeout`) so a completed product future always wins the race.

### P2-4 — Progress frames are never flushed on the cancel/timeout exits, breaking the module's own stated invariant
**Evidence:** `mcp/mod.rs:506` (`sink.flush().await`) sits **after** the `select!`, unreachable from the early `return`s at `mod.rs:477-481` (Cancelled) and `:495-499` (Timeout). The invariant is asserted twice in-repo: `mcp/progress.rs:19-23` ("that ordering is what makes rmcp's stateless response builder pick `text/event-stream`") and `mod.rs:378-380`. The comment at `mod.rs:464` ("frames drain when the sink drops") is not equivalent: dropping only closes the channel, while the spawned forwarder at `progress.rs:49-54` is fire-and-forget and never joined — already-queued frames may be emitted *after* the terminal result is built, or never reach the transport.
**Why it matters:** for the two longest-running failure modes (deadline, disconnect) a progressToken client's content negotiation (SSE vs plain JSON) and frame ordering become nondeterministic; on the legacy session path the detached task keeps a `Peer` clone alive and can push notifications onto a session stream after the terminal response.
**Fix:** `sink.flush().await` before each early `return` in `run_tool` (`flush` is already idempotent-guarded, `progress.rs:66-71`).

### P2-5 — `/mcp` auth failures emit no request event; REST's F08 does
**Evidence:** `mcp/auth.rs:14` calls the plain `require_api_token`; `events.rs:575`/`:620-631` (`ApiTokenLogged`) is the F08 extractor that `emit`s a 401 `Unauthorized` event, used only by `product/search.rs:66`, `product/extract.rs:23` and the research handler. No `events::emit` anywhere under `mcp/`.
**Why it matters:** every missing/invalid-token attempt against `/mcp` — the public, agent-facing surface — is invisible in `request_log`, the admin ring (`GET /api/request-logs`), the `error_kind` rollups and the B15 error-rate webhook, while the identical failure on `/api/search` is recorded. Brute force or a misconfigured MCP client is undiagnosable. (`metrics_middleware` at `lib.rs:164` counts the HTTP 401 but is not wired to the alert path.)
**Fix:** have `mcp_auth_middleware` emit the `auth_failure_fields` event, sharing one constructor with `ApiTokenLogged`.

### P2-6 — The `research` tool advertises knobs the deep loop silently discards
**Evidence:** all five fields live in one flat advertised schema — `mcp/params.rs:331` (`deep`), `:304` (`include_content`), `:298` (`social_max_results`), `:336` (`research_backend`), `:339` (`citation_format`) — and `validate_research_params` (`params.rs:354-366`) checks membership only, never interaction. Product behavior: `research.rs:88-90` returns from `deep_research_inner` **before** the `research_backend == Some("tavily")` pick at `:109`, and `citation_format` is plumbed only into the tavily job (`research.rs:1001`); the deep legs hard-code `include_content: Some(false)` (`research.rs:479`, `:557`) and contain no social leg at all (the only `social_max_results` consumer is `research.rs:168`). `scrape_top_n` also inverts meaning: non-deep `clamp(0,10)` with 0 = no scrapes (`research.rs:115`) vs deep `unwrap_or(3).clamp(1, DEEP_MAX_SCRAPE)` (`research.rs:470-473`), so `deep:true, scrape_top_n:0` scrapes one page.
**Why it matters:** the client receives `isError:false` results from a materially different product, with no warning field. `deep` + `researchBackend:"tavily"` is the worst case: the backend is ignored entirely, and `research.rs:107-108` acknowledges it in a comment while nothing at either boundary rejects the combination.
**Fix:** reject/warn on the incompatible combinations in `validate_research_params` (`deep` + `research_backend`/`citation_format`/`social_max_results`; `deep` + `scrape_top_n == 0`) and state the deep defaults in the field descriptions.

### P2-7 — No CORS/preflight path exists for `/mcp`; `MCP_ALLOWED_ORIGINS` cannot make a browser client work
**Evidence:** the auth layer is installed *outside* rmcp (`mcp/mod.rs:162-164`), so it sees every method before the transport, including `OPTIONS`; `serpotter-auth/src/lib.rs:32-54` (`extract_token`) reads only `Authorization: Bearer`/`x-api-key`, and browsers never attach those to a preflight → guaranteed 401. Grep for `Cors|allow_origin|OPTIONS` across `crates/serpotter-api/src` returns nothing, and the workspace `tower-http` feature list (`Cargo.toml:38`) is `trace, request-id, util, fs` — no `cors`. Yet `docs/ops/deploy.md:242` instructs "When exposing MCP to browser-origin clients, also set `MCP_ALLOWED_ORIGINS`", and `.env.example:23-26` names the browser-served MCP inspector.
**Why it matters:** setting the allowlist converts a 403 into a 401/uncors'd response — a browser page still cannot call `/mcp`. The documented mitigation for the known missing-Origin gap is therefore incomplete, and operators following it will conclude the server is broken.
**Fix:** skip auth for `OPTIONS` and add a `CorsLayer` driven by the same `MCP_ALLOWED_ORIGINS` list (requires the `cors` tower-http feature).

### P2-8 — Legacy session ids are bound to no identity; any valid token can drive or DELETE another tenant's session
**Evidence:** `mcp/mod.rs:113-114` mints/reuses sessions in one process-global `LocalSessionManager`; `mcp/auth.rs:9-23` authenticates the request and inserts a `TokenRow` but never records or checks a token↔session association. `tests/mcp_session.rs:96-143` drives DELETE with a session id from a different `initialize` on the same `AppState` and asserts only the status code.
**Why it matters:** a leaked `Mcp-Session-Id` lets one API token terminate (`DELETE`) or read from (`GET` SSE) another token's session — cross-tenant DoS and potential cross-tenant event delivery. UUIDv4 entropy is the *only* defense, and the 1 h keep-alive (`mod.rs:92`) is not an ownership boundary. The spec's own guidance ("validate the caller's authorization against the handle on every call"; bearer handles need entropy *and* bounded lifetime) points the other way.
**Fix:** key sessions per token id (wrap `LocalSessionManager` with a `session_id → token.id` map, reject mismatches with 404).

### P2-9 — No rate limiting or admission control on `/mcp`, which the 2026-07-28 spec lists under server MUSTs
**Evidence:** grep for `Throttle|RateLimit|concurrency_limit|tower::limit` across `crates/serpotter-api/src` → zero hits; the only bounds are the 2 MiB body limit (`lib.rs:95,162`) and provider-side key leases (`KEY_MAX_INFLIGHT`, product layer — not per-client). Each tools/call additionally spawns an unbounded, unjoined delivery task whenever the client supplies a `_meta.progressToken` (`mcp/progress.rs:49-54`) — attacker-controlled, per request.
**Why it matters:** the spec's Tools → Security Considerations requires servers to "Implement proper access controls" and "Rate limit tool invocations". A single token can enqueue unbounded research jobs (each fanning out to search + N scrapes + xAI synthesis against paid vendor keys) with no per-token ceiling; the keypool acquire timeout converts that into vendor spend plus queue growth rather than refusal.
**Fix:** add a per-token concurrency/queue cap (tower throttle keyed on `TokenRow.id`, or a bounded permit at the keypool) answering a retryable envelope.

### P3-10 — `MCP_SESSION_HEADER` is dead public API
**Evidence:** defined `mcp/mod.rs:89`, re-exported `lib.rs:29`, referenced nowhere else — every consumer hard-codes the literal `"mcp-session-id"` (`tests/mcp_session.rs:7,41,77,116,137`; `tests/mcp_tools.rs:14,32,271,337`).
**Why it matters:** the constant advertises a single canonical place for the header while the whole suite silently ignores it, so a rename would compile clean and break every test instead of being caught by one.
**Fix:** delete it, or use it in the tests so it becomes load-bearing.

### P3-11 — The `health` tool escapes both the error-envelope and the request-log contract
**Evidence:** `mcp/mod.rs:312` (`self.product.db.schema_version().await.ok()` collapses a DB error to `None` → `status: "not_ready"`), returned via `CallToolResult::success` at `mod.rs:321-323` as a bespoke `{status,schemaVersion,expected}` body with no `isError`, no `kind`, no `requestId`, no `retryable`; the handler takes no `Extension<Parts>` and never calls `events::emit`, so `health` produces no `request_log`/ring row and no duration/provider metric. `errors.rs:1-8` claims "**every** tool failure returns ONE JSON text block".
**Why it matters:** a hard DB outage reads to an agent as a healthy `isError:false` result, and the one tool an operator would use to detect it is the only MCP call that leaves no trace. (This is *not* an `outputSchema` violation — `health` correctly advertises none, pinned at `tests/mcp_stateless.rs:539-547`.)
**Fix:** route DB failure through `tool_error_structured("DatabaseError", …)` and emit a `/mcp/health` event like the other three tools.

### P3-12 — Extract `format`'s closed set is duplicated as literals and is the only case-sensitive knob
**Evidence:** `mcp/params.rs:369-378` matches `"question" | "highlights" | "markdown" | "text"` exactly and re-states the members in its error string; the same list is re-hardcoded downstream at `serpotter-product/src/extract/extract_url.rs:645-651`. There is no `VALID_EXTRACT_FORMATS` in `serpotter-core/src/validation.rs` (constants stop at `VALID_EXTRACT_PROVIDERS:65`), so REST cannot share it — `product/extract.rs:61-63` validates `provider` only. Every other MCP knob goes through `normalize_choice` (`params.rs:57-66`) and accepts `" Markdown "`/`"MARKDOWN"`.
**Why it matters:** an MCP client sending `format: "MARKDOWN"` gets a 400 while spelling variants are accepted everywhere else, and the two literal copies can drift silently — the product's copy decides the runtime route, the boundary's copy decides acceptance.
**Fix:** add `VALID_EXTRACT_FORMATS` to `serpotter-core::validation` and gate both sites with `normalize_choice`.

### P3-13 — `time_range` is a closed set for `search` and an unvalidated passthrough for `research`, on the same endpoint
**Evidence:** `mcp/params.rs:66` rejects unknown values for search (`normalize_time_range(...)?`, pinned at `params.rs:561-584`), while the research DTO documents the opposite at `params.rs:326` ("forwarded as-is when not a listed value") and `validate_research_params` (`params.rs:354-366`) never validates it; the raw string is copied into both research legs (`research.rs:124`, `:245`) and the deep passes (`research.rs:483`, `:561`).
**Why it matters:** a typo'd `timeRange` on `research` reaches a vendor as a 4xx, which `extract_err_log`/`search_err_log` map to `ProviderError` → the envelope carries `retryable: true` (`product/errors.rs:14-16`), actively teaching agents to retry a permanently invalid request against paid keys. Two identically named fields on one MCP endpoint with different acceptance rules is precisely the "misleads the client" failure `params.rs:41-53` was written to prevent.
**Fix:** call `normalize_time_range` from `validate_research_params`, matching the FU10 rationale already applied on REST.

### P3-14 — Stale tool/comment contracts and one no-op serde alias
**Evidence:** `mcp/params.rs:81` states "only firecrawl/tavily implement extract" while the same check validates against `VALID_EXTRACT_PROVIDERS`, which includes `exa` (`serpotter-core/src/validation.rs:63-65`) and is exercised with `" Exa"` at `params.rs:465`; `mcp/mod.rs:230` advertises the tool as "Scrape/extract a URL (Firecrawl first, then Tavily fallback)", omitting the exa `/contents` and the batch/`question`/`highlights` paths the same handler dispatches to (`extract_url.rs:569-573`); `mcp/params.rs:258` is `#[serde(default, alias = "urls")]` on the field named `urls` — a self-referential alias that can never match.
**Why it matters:** the tool `description` is the only documentation an LLM sees when choosing arguments, so naming two of four providers misroutes usage; the dead alias is the kind of line that gets copied to the next field and mistaken for real alias coverage.
**Fix:** correct the two descriptions/comments to the actual provider set and delete the self-alias.

### P1 — Holder-blind lease accounting: a late release mutates a *different* holder's row
**Evidence:** `crates/serpotter-db/src/keys/acquire_report.rs:111-114,142-145,183-186,215-218,239-242` — every release/report is `UPDATE api_keys SET inflight = … WHERE id = ?`; `nodes.rs:211-214,227-230,249-253` identical. `lease_token` appears nowhere in the workspace (grep). Reclaim runs *inside* the acquire transaction (`acquire_report.rs:53`, SQL `:7-8`) and full-zeros `inflight` for any row with `lease_until <= now`. The late release is not hypothetical: `crates/serpotter-product/src/hold.rs:171-183` `Drop` spawns a best-effort `keys.release(id)` precisely when the deadline aborts the attempt future (`api/src/product/mod.rs:91-99`).
**Why it matters:** after reclaim zeroes the row, the still-running request's release decrements the *new* holder's count and `CASE WHEN inflight <= 1 THEN NULL` clears a live `lease_until`. `KEY_MAX_INFLIGHT` then silently over-admits (vendor 429s / double-spend of one account), and demotion bookkeeping (`consecutive_fails`, `credits_remaining`) lands on the wrong lease. Already designed away in `docs/superpowers/specs/2026-09-11-…:24` ("Fix B"; status line 60 says steps 2-5 open) — still unmitigated.
**Fix:** add a per-acquire `lease_token` (schema v19) and scope every release/report/refresh with `WHERE id = ? AND lease_token = ?`.
